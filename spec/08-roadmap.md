# 08 — Roadmap

Phases are sequenced by dependency, not by calendar. Each has a concrete exit criterion.

## Current Status

The foundational core, VS Code formatter/linter integration, settings-schema verification (now a real generator, not a hand-maintained file — see "Schema generation" in [04-configuration.md](04-configuration.md)), profiles, range expansion, 73 bounded ABAP rules, and all 20 in-scope DDL/DCL rules are implemented (93 rules total). The current core suite has 472 passing tests. This roadmap describes the remaining route to broader compatibility; its original phase exit criteria have not been met as written.

**A pre-existing bug in the shared ABAP tokenizer (`parser/tokenizer.ts`) was found while porting `ALIGN_COND_EXPRESSIONS`, not yet fixed**: a string template's closing `|` (e.g. `|{ expr }|`) is misread as *opening* a new template segment, since the tokenizer tracks no "currently inside a template" state — everything after that `|`, up to the next `|`/`{`/end of text, is swallowed into one bogus token, silently dropping real tokens (confirmed via direct `tokenize()` test: `|{ a TIME = ISO } AM| && y.` loses `&&`, `y`, and the trailing `.` entirely). This affects every rule that scans raw tokens across such a template — not `ALIGN_COND_EXPRESSIONS` specifically — including `parseAbapCommands()`'s own Command-boundary detection. Fixing it is out of scope for a single rule's bounded port (shared infrastructure, needs its own dedicated fix and full regression pass across all 91 rules) and is called out here for future work.

Of the 79 upstream ABAP rules (`DECLARATIONS`, `SYNTAX`, `COMMANDS`, and `PRETTY_PRINTER` groups), `CAMEL_CASE_NAME` is explicitly **out of scope** (not deferred — see below), leaving an effective target of 78. 71 of those are ported as bounded, narrowly-provable TypeScript subsets, including:

- `UNUSED_PARAMETERS` — the roadmap previously assumed this needed cross-file signature lookup; rereading the Java source (`UnusedParametersRule.java` line 47) found it's explicitly documented as same-file only ("Parameters can only be checked if the method signature is found in the same code document"), which this port's per-file model handles fine. Adds a `" TODO: parameter <NAME> is never used (ABAP cleaner)` comment for an IMPORTING parameter never referenced in its method body, for a non-chained `METHODS` declaration whose every parameter has a simple `[VALUE(]name[)] TYPE simple-type [OPTIONAL] [DEFAULT ...] [##PRAGMA]` shape; EXPORTING/CHANGING/RETURNING parameters and removing stale TODO comments are not yet handled.
- `LOCAL_DECLARATION_ORDER` — the roadmap previously deferred this as needing robust whole-method statement/comment-boundary detection; rereading the Java source found a safe bounded slice: upstream's `CONSTANTS` default (`METHOD_START_KEEP_ORDER`) needs only relocation preserving original order, not the usage-order scan `DATA`/`STATICS`/`FIELD-SYMBOLS` need by default. Relocates a simple, non-chained, comment-free `CONSTANTS name TYPE simple-type VALUE literal.` declaration found anywhere in a method/form/function body to immediately after the last already-correctly-positioned leading `CONSTANTS`, refusing the whole body on a `BEGIN OF` structure or dynamic `ASSIGN`; `TYPES`/`STATICS`/`DATA`/`FIELD-SYMBOLS` grouping and usage-order reordering are not yet handled. Ships default-off, matching upstream's own `isActiveByDefault() = false`.
- `ALIGN_ASSIGNMENTS`, `ALIGN_ALIASES_FOR`, `ALIGN_CLEAR_FREE_AND_SORT` (bounded to `CLEAR:`/`FREE:` chains), `ALIGN_METHODS_REDEFINITION` (bounded to single-line, non-`FINAL` declarations), `ALIGN_METHODS_FOR_TESTING` (bounded to single-line `METHODS <name> FOR TESTING.`, no `ABSTRACT`/`RAISING`), `ALIGN_DECLARATIONS` (bounded to non-`TYPES`, non-`BEGIN OF` `DATA`/`CONSTANTS`/`FIELD-SYMBOLS name TYPE type [VALUE value].`, both as a consecutive run and as one chain's items) — six `ALIGN_*` rules now share one narrow, purpose-built alignment engine (`rules/syntax/align-helpers.ts`'s `alignColumnsLeftAligned` — left-aligned, single-token-cell columns only; upstream's `AlignTable`/`AlignColumn` add right-alignment, forced cross-column indents, and overlength-line mid-cell splitting this engine deliberately doesn't replicate, see the file header). `DDL_ALIGN_ENTITY_PARAMETERS`/`DDL_ALIGN_SOURCE_PARAMETERS` (below) reuse the same engine across the ABAP/DDL toolkit boundary, proving it generalizes rather than being a one-off. Every "consecutive run" `ALIGN_*` rule requires each row to sit on its own distinct source line — two matching statements crammed onto one physical line are left unaligned, since alignment is inherently a vertical/cross-line concept (a real bug, caught by an interaction with `ONE_COMMAND_PER_LINE`/`DECLARATION_CHAIN` in `engine.test.ts`, fixed across all five affected rule files; see "Two more real bugs" below).
- `ALIGN_ABAP_DOC` — unlike every other `ALIGN_*` rule, upstream doesn't use `AlignTable` here at all; it rewrites each `"! @parameter/@raising/@exception <name> | <text>` comment token's own text with computed keyword/name padding baked in. Works directly on the token stream rather than `parser/commands.ts`'s statement list, since a standalone leading comment is merged into the *following* statement's Command in this port's parser rather than getting a Command of its own — the per-comment-line granularity this rule needs only exists at the token level.
- `ALIGN_LOGICAL_EXPRESSIONS` — initially assessed (like its DDL twin below) as needing a full port of upstream's `LogicalExpression`/`TreeAlign`/`TreeAlignColumn` subsystem (~1,264 lines: a recursive operator-precedence tree plus a tree-aware column-matching layout algorithm), a genuinely new architecture-phase-sized undertaking. Re-researched via a dedicated fork before committing to that: `TreeAlign` turns out **not** to decide line breaks at all (every cell's `lineBreaks` passes through unchanged from the source; it only recomputes horizontal indent of whatever line layout already exists), and upstream's shared default for `IF`/`ELSEIF`/`CHECK`/`WHILE` (`AlignStyle.DO_NOT_ALIGN`) never repositions the triggering keyword's own line. That made a much smaller bounded slice possible without the tree at all: a *flat* chain of comparisons joined only by `AND` or only by `OR` (never mixed, no `NOT`/parens/`EQUIV`), every comparison using the identical single symbolic operator (`=`,`<>`,`<`,`>`,`<=`,`>=` — narrowed to identical-operator-only after a design review caught that upstream's actual default right-aligns the comparison-operator column, which this port's left-align-only engine can only reproduce exactly when every operator in the chain has equal width) with single-token operands, one condition per source line. The trigger line is left untouched; only the `AND`/`OR` continuation lines are aligned against each other, reusing `alignColumnsLeftAligned` completely unchanged — no new engine capability needed. `NOT`, parentheses, predicate expressions (`IS INITIAL`/`IS BOUND`/`IN`/`BETWEEN`), and keyword-style operators (`EQ`/`NE`/...) all refuse naturally as a side effect of the strict 3-token-per-condition shape check, without needing their own exclusion logic.
- `DDL_ALIGN_LOGICAL_EXPRESSIONS` (DDL) — the DDL twin, sharing the same bounded-shape parser (`syntax/logical-chain.ts`'s `parseConditionChain`) via the ABAP/DDL toolkit boundary. Finds each top-level `JOIN`/`ASSOCIATION`'s `ON` condition by reusing `DDL_POSITION_JOIN`/`DDL_POSITION_ASSOCIATION`'s own phrase/condition-span scanning (`position-join-association.ts`, now exporting `findTopLevelJoinAndAssociationPhrases`/`findOnIndex`/`conditionEndIndex` for this purpose) rather than duplicating it. Upstream's actual default for DDL `ON` is `AlignStyle.LEFT_ALIGN`, not `DO_NOT_ALIGN` — documented accurately in the file's header rather than assumed, since the two styles are verified to coincide only for this specific paren-free flat-chain shape (`TreeAlign`'s bracket-repositioning branch, the only thing that would make them diverge, never triggers without a `NOT`/parenthesis column). `WHERE`/`HAVING`/`WHEN`/path-expression-filter conditions (also handled by upstream's rule) are not recognized — only `JOIN`/`ASSOCIATION` `ON`.
- `ALIGN_SELECT_CLAUSES` — a second look at the 5 rules needing upstream's `SelectQuery`/`SelectClause` classifier (below) found one, `AlignSelectClausesRule`, has its own genuinely bounded slice independent of the classifier: upstream's real default (`MainQueryOneLinerAction = KEEP_EXISTING`) never creates a one-liner — confirmed against upstream's own `testKeepOneLiners()` — so this port only repositions `FROM`/`WHERE`/`GROUP BY`/`HAVING`/`ORDER BY`/`INTO`/`APPENDING` onto their own line at `SELECT`'s column + 2 for a statement that's *already* multi-line, architecturally identical to `DDL_POSITION_CLAUSES`'s keyword-repositioning pattern (not `alignColumnsLeftAligned`-style column alignment at all, despite the rule's name). Reuses `ddl/position-helpers.ts`'s `breakBeforeWithIndent`/`condensePhrase`/`applyEdits` for the ABAP side, exactly as `align-clear-free.ts` already does. Refuses the whole statement (reusing `parser/control-blocks.ts`'s `isNonLoopSelect`, exported for this purpose, rather than re-deriving `SELECT...ENDSELECT` loop detection) on the loop form, `FOR ALL ENTRIES`, `%_HINTS`, or a second `SELECT` keyword anywhere — a single check that conservatively covers subqueries *and* `UNION`/`INTERSECT`/`EXCEPT` chains together, since all three upstream constructs syntactically require a second `SELECT`. A design review caught that upstream's default also keeps a `FROM` with no `JOIN` glued behind the `SELECT` list rather than always forcing it onto its own line — implemented as an explicit exception, not silently dropped. This shared refusal vocabulary was later extracted into `select-refusals.ts`'s `parseSimpleSelectCode()` (see `ALIGN_SELECT_LISTS` below) once a second rule needed it too.
- `ALIGN_SELECT_LISTS` — a user-approved architecture-phase investigation into the full `SelectQuery`/`SelectClause` classifier and `AlignCellTerm` (multi-token cell) engine extension (both confirmed real, clean, reusable infrastructure by direct reading of the Java source) found they only cash out into ONE new rule right now, not the four originally hoped for (`AlignSelectFromRule`/`AlignParametersRule`/`AlignMethodsDeclarationRule` all have load-bearing complexity — nested multi-table-level tracking, large multi-axis config interaction, an extra base-class family — that doesn't reduce to a small bounded slice). `AlignSelectListsRule` did: upstream classifies each SELECT-list field "simple" (one token) or "complex" (more than one token, OR one token containing `~` since `ConsiderTildeAsComplex` defaults true) and forces the whole clause multi-line if ANY field is complex (an OR-reduction); this port narrows that to an AND-reduction — every field must be complex — a strictly conservative subset that never fires when upstream's real default wouldn't also go multi-line. While drafting the implementation, a design review caught that "2-column Term-based AS-alignment" (the concrete plan the classifier research recommended) can't be added safely yet: real select lists commonly mix fields with and without `AS`, giving rows an inconsistent cell count that `alignColumnsLeftAligned` (which pads every column boundary for every row unconditionally) can't tolerate without new, unvetted capability — so this first cut ships as a pure repositioning rule (one field per line, hang-indented to the first field's column, reusing `align-clear-free.ts`'s exact technique) with `AS`-column alignment explicitly left undone and documented as such, rather than guessed at. The review also caught a real faithfulness gap in the first draft — the single-line refusal check was missing from the design entirely, which would have made the rule explode an already-single-line statement upstream's default leaves untouched — fixed by routing both `ALIGN_SELECT_CLAUSES` and `ALIGN_SELECT_LISTS` through the same shared `select-refusals.ts` gate (extracted from `ALIGN_SELECT_CLAUSES`, which was re-verified byte-for-byte unchanged against its existing tests plus 3 new boundary-condition fixtures after the refactor).
- `DDL_ANNO_NESTING` — a second look (below `DDL_ANNO_NESTING` was previously assessed as having no safe partial slice at all) found a genuinely provable bounded case after a design review caught that the first attempt's premise was wrong: "always render multi-line, skip the one-liner decision" is NOT a safe narrowing in general (`MaxOneLinerElemCount` defaults to 4, so a group of 2-4 members really can collapse to one line by default; assuming otherwise would have silently diverged from real default output). The genuinely safe case: a group of **5 or more** members is *never* a one-liner candidate regardless of width under the default config, so "always multi-line" is provably correct, not approximated, at that size. Nests a run of 5+ CONSECUTIVE simple annotations (`@path: single-token-value`, no existing `{}`/`[]` structure, no trailing comment — both excluded for free by one "exactly 3 tokens" shape check, no dedicated exclusion logic needed) sharing an exact parent path of 3+ segments (a conservative floor matching `NestingMinDepth`'s default `LEVEL_3` — may refuse a few cases upstream's default would also nest, but never nests one it would leave flat) into one `@parentPath: { name: value, ... }` annotation, hang-indented to the brace column and member-name-padded (matching `DdlAnnotationWriter`'s real indent/padding mechanism, read directly rather than assumed), with grouping requiring the annotations be already-adjacent (no blank line or comment gap) rather than needing upstream's real alphabetical resort — conservative-only, since already-adjacent same-prefix annotations are exactly what a resort would also group.

- `ALIGN_WITH_SECOND_WORD` — a final second-look pass (given this session's repeated track record of finding bounded slices in things assessed "too large") found upstream's own source contains a `// TODO: or would it be better to use an include list?` comment acknowledging the exact alternative this port takes: instead of upstream's long, risky EXCLUDE list (`isDeclaration`/`isAssignment`/`isAbapSqlOperation`/etc.), this port uses a small INCLUDE list — just `READ`/`LOOP`, chosen because both are unambiguous internal-table/loop operations with no Open-SQL-statement homonym (unlike `INSERT`/`DELETE`/`MODIFY`/`EXPORT`/`IMPORT`, each of which can ALSO be a database operation this port has no classifier to distinguish, so they stay excluded). Repositions a small fixed continuation-keyword set (`WITH`/`INTO`/`ASSIGNING`/`WHERE`) to the column of the trigger statement's own second word, reusing `breakBeforeWithIndent` — pure token re-indentation, no alignment engine needed.
- `ALIGN_COND_EXPRESSIONS` — the same pass found a real escape hatch for `COND #( WHEN ... THEN ... ELSE ... )` expressions with exactly one `WHEN` branch: upstream's own default (`SimpleStyle = VERTICAL_LAYOUT`) puts `WHEN`/`THEN`/`ELSE` each on its own line at a fixed indent — confirmed against `AlignColumn.java`'s actual mechanism (`setForceLineBreakAfter`/`setForceIndent(0)`), not just inferred from an example. `SWITCH` (a structurally different `operand`-before-`WHEN` shape), a `LET ... IN` prefix, and the multi-`WHEN` tabular case (genuinely needing `AlignTable`/width-simulation) are all out of scope and refuse the whole expression. Porting this surfaced a pre-existing bug in the shared ABAP tokenizer (see "Current Status" above) — a string template's closing `|` is misread as opening a new template segment — which this rule documents as an inherited, unfixed limitation rather than silently mishandling.

One `SYNTAX`/`ALIGNMENT` rule and 5 `ALIGN_*` rules are deliberately deferred rather than faked:

- `ALIGN_*` (5 remaining rules) — `rulehelpers/AlignTable.java`/`AlignColumn.java`/`AlignLine.java`/`AlignCellTerm.java` (1,214 lines total) implement a considerably more general layout engine than "rows → columns → pad" — right-alignment per column, forced max-indent relative to another column, forced-line-break-after columns, mono-/multi-line cell width modes, and overlength-line fallback logic. It is not tied to the Command/Token object model in a way that blocks a token-stream port, but building that full generality is a large investment; the 13 ported rules above (including `ALIGN_LOGICAL_EXPRESSIONS`, `ALIGN_SELECT_CLAUSES`, `ALIGN_SELECT_LISTS`, `ALIGN_WITH_SECOND_WORD`, and `ALIGN_COND_EXPRESSIONS`, whose *general* cases were reassessed as out of scope but whose bounded cases were not) prove the narrow-engine approach generalizes further than initially assumed. `AlignFormDeclarationRule`/`AlignPerformRule` were read in full and confirmed, not merely assumed: both use real `AlignCellTerm`-based multi-column tables with sparse cells and `forceLineBreakAfter`/`forceIndent` column behaviors this port has never built, targeting the genuinely obsolete `FORM`/`PERFORM` procedural syntax Clean ABAP itself discourages — no default-config narrowing removes the sparse/Term-cell requirement even for the simplest 2-parameter case. `AlignCondExpressionsRule`'s own multi-`WHEN` tabular case (as opposed to the single-`WHEN` case ported above) stays deferred for the same reason. `AlignMethodsDeclarationRule` was read in full: its real default (`AlignConsecutive = ONE_LINERS`, changed from `NEVER` in 2022) requires grouping multiple `METHODS` statements into one shared cross-Command alignment table, the same class of infrastructure blocking the DDL rules below, plus a dedicated base class (`AlignDeclarationSectionRuleBase`) this port has no equivalent of. `AlignParametersRule` (1069 lines, the largest single rule in the whole upstream tool) has two separate width-simulation thresholds (`MaxLineLength`/`MaxLineLengthForSingleLine`) load-bearing even for its simplest single-parameter case — no escape hatch found. `AlignSelectFromRule` was reassessed by reading `executeOn`'s actual method body (not just its config defaults, which misleadingly suggested simplicity since `AlignAsAcrossJoins`/`AlignOnAcrossJoins` both default `false`): even with cross-join alignment off, it still builds a full multi-level `AlignTable` stack (one table per parenthesis-nesting level, for nested sub-selects) with `AlignCellTerm` cells and per-column indent *formulas*, reconfirming the original "too large" verdict.

**Out of scope:** `CAMEL_CASE_NAME` and `DDL_CAMEL_CASE_NAME` (below) fix ABAP/DDL identifier casing to match a CDS view's/field's canonical mixed-case spelling, by looking it up in upstream's `CamelCaseNames` lookup (`rulehelpers/CamelCaseNames.java` + `camel_case_field_names.txt`/`camel_case_view_names.txt`, ~212k/~153k lines, a `text.toUpperCase().hashCode()` → case-bitmap hash table, not an enumerable word list). Porting it is possible (a JS `String.hashCode()` reimplementation, a resource-format parser, and ~2–4MB of bundled data), but was decided against: it only fixes cosmetic casing, has zero effect on any custom (non-SAP-standard) CDS view, its value ceiling shrinks as SAP ships new views the table doesn't know about, there are no golden test fixtures to verify hash-exactness against, and upstream itself doesn't rate it essential (active by default, but excluded from the essential profile). Decision made 2026-09-18; revisit only if a verifiable, current name-casing data source becomes available.

`INSET` (reindentation), `UNUSED_VARIABLES`/`FINAL_VARIABLE` (declaration cleanup), and `UNUSED_PARAMETERS`/`LOCAL_DECLARATION_ORDER`/`ALIGN_*` above are implemented as bounded subsets despite requiring some cross-command scanning, since a single- or two-pass scan (rather than a genuine move/rewrite of the parse tree) was enough to prove each safe; see the "Ported from" header comment in each rule file for the exact scope and refusal conditions. `LOCAL_DECLARATION_ORDER` runs before `UNUSED_PARAMETERS` in the pipeline specifically so a relocated `CONSTANTS` declaration is never mistaken for "already has a comment attached" by `UNUSED_PARAMETERS`'s own inserted TODO comments.

Of the 21 upstream DDL/DCL rules, `DDL_CAMEL_CASE_NAME` is explicitly **out of scope** (see the ABAP `CAMEL_CASE_NAME` callout above — same reasoning, same `CamelCaseNames` dependency), leaving an effective target of 20. All 20 of those are now ported as bounded subsets (see each file's "Ported from" header comment for its exact scope and refusal conditions), proving the DDL language-dispatch path end-to-end (`TypeScriptCleanupEngine.clean()` now routes `DDL`/`DCL` sources to a separate rule pipeline instead of a no-op):

- `DDL_EMPTY_LINES_WITHIN`, `DDL_EMPTY_LINES_BETWEEN` — the latter standardizes blank-line counts at 5 of 8 upstream section boundaries (annotations→DEFINE, before/after the select-list braces), all via the reusable `ensureAtLeastOneBlankLineBefore`/`capBlankLinesBefore` helpers in `rules/ddl/position-helpers.ts`, and never creates a line break where none exists.
- `DDL_SPACES_AROUND_SIGNS`, `DDL_SPACES_AROUND_BRACKETS`, `DDL_ANNO_LAYOUT` — the last condenses an annotation's dotted path and standardizes spacing around every colon inside it, but not its nesting/one-liner/alignment layout (that remains `DDL_ANNO_NESTING`'s and the rest of `DDL_ANNO_LAYOUT`'s job, both deferred — see below).
- `DDL_POSITION_BRACES`, `DDL_POSITION_CLAUSES`, `DDL_POSITION_SELECT`, `DDL_POSITION_DEFINE` — each finds its trigger keyword(s) via plain bracket-depth-0 token scanning (`rules/ddl/position-helpers.ts`'s `breakBeforeWithIndent`/`condensePhrase`/`nextCodeIndex` etc.) rather than the Command-tree navigation (`getParent()`, siblings, `command.addIndent()`) upstream uses; `DDL_POSITION_DEFINE` also uses a fixed structural-keyword list in place of upstream's full `getDdlOrDclEntityNameToken()` pattern matcher.
- `DDL_POSITION_JOIN`, `DDL_POSITION_ASSOCIATION` — the roadmap previously deferred these on the assumption that `BreakBeforeCondition = IF_MULTI_LINE_FOUND`'s whole-file `prepare()` pre-scan needed real cross-command infrastructure; rereading the Java source found it reduces to one shared boolean (`viewContainsMultiLineJoinCond`/`...AssociationCond`) computed by a first pass over the token stream, then applied uniformly in a second pass — the same two-pass technique used throughout this port's other position rules, not new infrastructure. Ported: the keyword-phrase break/condense and the two-pass condition break. Not ported: the `WITH DEFAULT FILTER` clause, breaking before the data source (`NEVER` by default, so already a no-op), and re-indenting a multi-line condition's continuation lines by the delta its `ON` keyword moved (`command.addIndent()` — upstream does this, this port does not, so a moved multi-line condition's `AND ...` lines keep their old column).
- `DDL_TYPO` — reuses the same narrow typo-correction table as the ABAP `TYPO` rule, applied to DDL/DCL comments; the roadmap previously assumed this needed the `CamelCaseNames` dictionary, which was incorrect for this path (only the upstream rule's annotation-value-TODO and British/American-conversion features do, and those are not ported).
- `DDL_ALIGN_ENTITY_PARAMETERS` — the first `DDL_ALIGNMENT` rule, and the natural follow-up to `DDL_POSITION_DEFINE` (which already breaks/indents `WITH PARAMETERS` but explicitly punts on the parameter list itself). Finds the `WITH PARAMETERS` clause, and if every parameter has the simple shape `<name> : <single-token-type>`, enforces indent 4 and left-pads the name/colon columns, reusing `align-helpers.ts` across the ABAP/DDL toolkit boundary. Matching upstream's own "if one parameter is blocked, cancel alignment entirely," a single parameter with a multi-token type (e.g. `abap.char( 10 )`) cancels alignment for the *whole* clause rather than skipping just that parameter.
- `DDL_ALIGN_SOURCE_PARAMETERS` — column-alignment-only slice of the 3-operation upstream rule (parenthesis repositioning, colon alignment, post-`)` alias positioning): finds every `select from|join|on <entity>( ... )` invocation and, if every parameter has the simple shape `<name> : <single-token-value>` with each parameter on its own source line, left-pads the name/colon columns, reusing the same `align-helpers.ts` engine again. A dotted path like `$parameters.P_AnyParam` is one "word" token under this port's DDL tokenizer (`.` isn't DDL punctuation), so it qualifies as simple; a multi-token value (e.g. an arithmetic expression) cancels alignment for the whole clause. Repositioning the opening parenthesis and the `AS <alias>` remain deferred, same as before.
- `DDL_ALIGN_FUNCTION_PARAMETERS` — a second look at the 2 unexplored `DDL_ALIGNMENT` rules found this one is nearly a direct extension of the already-shipped source/entity-parameter technique: finds every `(` preceded by a word token containing a top-level `=>` (CDS's named-parameter call syntax, e.g. `currency_conversion( amount => a, source_currency => b )` — no hardcoded function-name whitelist, since the `=>` presence itself is the trigger and never appears inside a `:`-separated data-source/entity-parameter list, so the rules' triggers never overlap) and, if every parameter has the simple shape `<name> => <single-token-value>`, aligns via the same `alignColumnsLeftAligned` engine. A design review confirmed refusing the whole call on one bad parameter (matching the sibling rules' behavior) is a deliberately *stricter* choice than upstream's own real per-parameter selective matching, and that upstream's default also collapses the opening-paren/first-parameter line break and normalizes post-`)` blank lines — none of that line-break positioning is ported, only existing lines' column padding. Nested function calls align independently, since every `(` in the file is scanned as its own unit.
- `DDL_ALIGN_FIELD_LISTS` (`GROUP BY` only) — the other rule from that second look: upstream's own default config makes this simpler than expected, not harder — `ComplexGroupByListLayout`/`SimpleGroupByListLayout` both default to `MULTI_LINE`, and `determineLayout()` has an early return whenever the two configs are equal, so the per-field complexity classification is *never evaluated* under default settings; `GROUP BY` is unconditionally exploded to one field per line regardless of complexity or existing layout. This port reproduces exactly that (no classification needed), hang-indenting each field after the first to wherever the first field already sits — the same technique `align-clear-free.ts`/`ALIGN_SELECT_LISTS` use — rather than upstream's own `GroupByListPos` indent formula (which also relocates the first field itself onto the `GROUP BY` line; not implemented). A design review caught a real misparse risk in the first draft: the field-collection scan needed the statement terminator `;` added to its boundary-keyword set, or a `GROUP BY` at the end of one CDS artifact in a multi-artifact file would misparse the next artifact's leading tokens as more fields. The DDIC-view parenthesized name list — this rule's other, unrelated upstream target, with different position semantics — is not handled.
- `DDL_ALIGN_DATA_SOURCES`, `DDL_ALIGN_SELECT_LIST` — the last 2 `DDL_ALIGNMENT` rules, unlocked by a new shared engine capability, `align-helpers.ts`'s `alignColumnsWithOptionalCells` (Term cells + sparse TRAILING columns, added alongside the existing `alignColumnsLeftAligned` rather than replacing it — verified against `AlignTable.java`'s real null-cell mechanism, including a review-caught bug in the first draft: a column empty across every row must contribute zero width, not `width+1`, or it injects a spurious space before every row's next cell). Both rules drop upstream's `KEYWORDS`/`KEY_OR_VIRTUAL`-style LEADING sparse column entirely rather than approximate it — the engine doesn't support a missing column 0 (upstream's real engine rewrites each token's absolute position from scratch, which doesn't translate to this port's "only pad gaps between already-existing cells" edit model) — `DDL_ALIGN_DATA_SOURCES` simply doesn't align the `JOIN`/`ASSOCIATION` keyword phrase into a column (already positioned by `DDL_POSITION_JOIN`/`DDL_POSITION_ASSOCIATION` anyway), and `DDL_ALIGN_SELECT_LIST` folds a leading `KEY`/`VIRTUAL` into its `ELEMENT` cell's own span instead of giving it a separate column. `DDL_ALIGN_DATA_SOURCES` groups each top-level `FROM` with its following `JOIN`/`ASSOCIATION` phrases (reusing `position-join-association.ts`'s existing phrase-scanning, confirming the "needs real cross-Command infrastructure" premise was wrong — this port's flat DDL token stream never needed a Command tree for this); `DDL_ALIGN_SELECT_LIST` refuses the whole list if it contains any comment, a real (not merely convenient) narrowing given upstream's comment-integration machinery has no analog here. Both rules found and fixed the same real bug during implementation: naively padding between two cells that already sit on DIFFERENT source lines (e.g. an `ON` condition `DDL_POSITION_JOIN` already pushed onto its own line) would destructively merge that line back, since this port's edit model always REPLACES the gap between two cells with pure spaces — fixed by excluding a cell from column alignment (leaving it untouched at its existing position) whenever it isn't on the same line as the row's previous included cell, now documented as a caller responsibility in `align-helpers.ts`'s own header.

All 20 in-scope DDL rules are now ported; none remain deferred. (`DDL_ANNO_NESTING`'s general case — below the 5-member/3-segment bounded slice already ported, see above — remains a documented gap within that one rule, not a separate deferred rule: `DdlAnnotationScope`/`DdlAnnotationCommandWriter` build a real flat-leaf annotation model, group leaves cross-command by shared path prefix, run a *simulated dry-run write pass* purely to measure resulting line lengths before deciding which smaller nesting ranges fit on one line, then serialize the whole restructured scope into brand-new tokens and diff against the original — there is no safe partial slice for that part, since a below-threshold group's one-liner decision genuinely depends on the width of every other annotation sharing its scope. `determineTablesInArrays()`, array/table value handling, is a further separate, more complex piece not attempted either.)
- `DDL_ALIGNMENT` (4 remaining rules) — uses the same `AlignCellTerm`/`AlignColumn`/`AlignTable` multi-column layout infrastructure as ABAP `ALIGN_*`; same status as ABAP `ALIGN_*` above. `DdlAlignDataSourcesRule`, `DdlAlignFieldListsRule`, `DdlAlignFunctionParametersRule`, `DdlAlignSelectListRule` are not yet investigated in depth.

Parentheses spacing (functions/ABAP types/arithmetic) within the already-ported `DDL_SPACES_AROUND_BRACKETS` itself also remains unhandled, needing the built-in-function/ABAP-type name lists this port does not have.

**Two real bugs were found and fixed while porting this round's rules**, both in shared infrastructure other rules also depend on:

- `annotation-ranges.ts`'s `isLineStart()` only recognized an `@annotation` line as line-starting when the `@` sat at literal column 0, silently failing to recognize (and thus not skipping) an *indented* annotation — the common case for a parameter- or field-level annotation nested under `WITH PARAMETERS` or a select list. Every already-shipped rule that skips annotation content via this helper (`DDL_SPACES_AROUND_SIGNS`, `DDL_SPACES_AROUND_BRACKETS`, `DDL_ANNO_LAYOUT`, every `DDL_POSITION_*` rule) had this same latent gap; none of their existing tests happened to exercise an indented annotation, so it went unnoticed until `DDL_ALIGN_ENTITY_PARAMETERS`'s test suite hit it directly. Fixed to check "only whitespace precedes this token on its own line," not literal column 0.
- `position-helpers.ts`'s `applyEdits()` applied edits via `Array.reduceRight`, which is only correct when the `edits` array happens to already be in descending-start-offset order — true for every rule that builds its edit list via a single left-to-right token scan (all of them, until now), but false for `DDL_ALIGN_ENTITY_PARAMETERS`, which computes an indent pass and a separate column-alignment pass that interleave in offset-space without being array-sorted. Fixed by sorting defensively inside `applyEdits()` itself, protecting every current and future caller from the same class of bug rather than requiring each caller to get the ordering right by construction.

**A third real bug was found and fixed after adding `ALIGN_DECLARATIONS`:** every "consecutive run" `ALIGN_*` rule (`ALIGN_ASSIGNMENTS`, `ALIGN_ALIASES_FOR`, `ALIGN_METHODS_REDEFINITION`, `ALIGN_METHODS_FOR_TESTING`, `ALIGN_DECLARATIONS`) grouped array-adjacent matching `Command`s into an alignment run without checking they sit on different source lines. This went unnoticed until `ALIGN_DECLARATIONS` (default-enabled) fired on an existing `engine.test.ts` fixture — two `DATA` statements deliberately crammed onto one line to test `ONE_COMMAND_PER_LINE`'s default-off behavior — and inserted a spurious extra space, since "aligning" two statements that share a line is meaningless (alignment is inherently a vertical/cross-line concept). Fixed by requiring each row's first token to sit on a source line distinct from the previous row's in all five files; `engine.test.ts`'s two affected fixtures were updated to reflect `ALIGN_DECLARATIONS` now correctly firing once `ONE_COMMAND_PER_LINE`/`DECLARATION_CHAIN` split their single-line/single-line-chain input onto separate lines.
